# Verify-only

Input is a canonical allowed local Git repository, BASE commit/ref, Candidate commit/ref and original intent. Both refs are frozen to commit/tree identities. Dirty working trees and a HEAD beyond BASE are allowed; verification reads committed objects and does not checkout, commit, fetch or modify the repository.

`POST /api/verify-only` starts independent oracle authoring and BASE admission. `GET /api/verify-only/:id` shows test names, assertion summaries, assurance, red-on-base results and unsupported claims. `POST /api/verify-only/:id/approve` requires the exact review hash. No Candidate code executes until approval. There are no analysis, planning or Builder stages.

The existing protected materializer and process-isolated observer/judge are reused. BASE versions of existing test files are restored; dependency changes/security review flags remain non-passing. Strict native report correlation, exactly one test, no skips/zero-test PASS and certified process cleanup remain authoritative. Python SDK returned object attributes can be captured as observations; the judge never imports Candidate code. Direct calls are IN-PROCESS and retain the previously documented observation-forgery residual risk.

V2 freezes every claim as REQUIRED or ADVISORY before admission. The current authoring path conservatively makes intent claims and native regression/scope guards REQUIRED; it does not infer optionality from wording. Advisory scoring remains available for explicitly classified evidence. Explicit intent cannot silently become advisory. Unsupported or rejected checks stay visible as NOT CHECKED or ERROR. Per-claim outcomes are PASS, FAIL, NOT CHECKED, ERROR, CANCELLED and STALE. VERIFIED requires at least one REQUIRED claim and every REQUIRED claim passing on the bound artifact. ACCEPT WITH WAIVER is a separate immutable human decision naming all unmet REQUIRED claims and a reason; it never changes test results to PASS.

Fixed techniques now include actual browser/DOM fixtures for provider/API-dependent UI, public CLI fixture setup with filesystem/network observations, repeated synchronized public CLI calls for concurrency, and BASE-restored native regression suites. The judge remains process-separated and never imports Candidate code. UI hosting shims apply only to navigation, socket/motion hosting, not the asserted application behavior. Claims name supplied BASE targets and quote intent; CHANGE checks must also respond to independent intent-targeted correct/wrong implementations. Unrelated UI cannot earn admission merely by rendering.

Each new CHANGE must have a genuine assertion failure on BASE, PASS on an independently authored correct reference and FAIL on a plausible wrong implementation. Reference authoring is a separate tool-free read-only Codex thread receiving public intent and BASE only, never Candidate or check code. Regression guards must pass BASE. Concurrency admission uses three 500-pair BASE samples; each must fail for observed race outcomes. Correct reference and Candidate sampling use 2,000 pairs. Failure rate and a quantified residual-risk note are retained; sampling does not prove race elimination.

Evidence records Candidate export, restored-test overlay, immutable recipe/required list and executed checks separately. Changed content or unavailable evidence returns STALE, including after restart. Historical v1 records are retained byte-for-byte and do not qualify as v2 VERIFIED. Every automatic stage has a deadline; uncertain execution/cleanup and environment failures are ERROR rather than Candidate failure. Abandon is idempotent and fences pending work.

The observer permits signals only to same-sandbox child targets, allowing owned timeout cleanup. Self/parent, recorder, harness and separate judge signals remain denied. The judge retains deny-signal. Structured output from every real AI step is retained, including malformed and later schema-rejected output, with credential redaction; temporary provider files are removed.

Review is persisted; interrupted authoring/verifying becomes ERROR on restart and never automatically replays. Approval also binds the protected evaluator identity. No model/runtime change to the Builder.

Abandon can be requested without a reviewed Spec. It fences new work, interrupts only that Mission's active preparation, stops owned execution and records ABANDONED only after cleanup is certified. Uncertain cleanup remains Needs You with the durable request. An already-recorded Land side effect/journal still requires reconciliation; Abandon never erases a branch or changes a recorded Land permission.
