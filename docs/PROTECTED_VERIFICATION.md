# Protected verification — Breakout 9

Frozen Candidate → current accepted artifacts → immutable recipe → fresh workspace → protected checks → durable claim evidence.

The recipe is constructed from accepted Contract/Plan/Evaluation revisions and stored pre-Build sources. Candidate changes never select their oracle. The initial automatic template covers only the named Boolean denial/allowed-effect fixture with the stored `apply_proposal(allowed, effect)` interface. Its protected launcher validates a bounded Python AST before execution: one exact Boolean function, Boolean branches/returns, direct effect calls and optional bounded trusted sleep. Imports, reflection, extra globals, assignments and uncontrolled calls are inconclusive. This prevents Candidate code from controlling the completion witness. It observes finite input cases; it does not certify permission protocols, stale grants or universal program correctness. Claims without a precise trusted mapping remain unsupported. Manual results are identified as local-operator judgments, with a required note and timestamp.

Materialization uses the archived complete Candidate tree, without relying on a source checkout or Builder workspace. The complete materialized tree is checked before execution and before finalization. The existing archive does not preserve the BASE commit, so an objective BASE-to-Candidate static diff is inconclusive when BASE objects are unavailable. Diff evidence is still bound by its recorded SHA256. No remote fetch or dependency installation occurs.

The coordinator owns recipes, the evaluator bundle, results and evidence outside Candidate authority. Candidate code runs only after a native sandbox is installed. The execution profile denies network, process creation/execution/signalling, control-directory access, user/private configuration access and writes outside current disposable scratch. Protected bundle and Candidate workspace are read-only during execution. The native profile uses explicit user/private/control deny roots; reads outside these roots remain available to native trusted runtime probes. The accepted Candidate statement set has no general filesystem/import facility. System runtime/framework reads remain available; native isolation does not provide a microVM, resource virtualization or a universal hostile-code proof. Missing native isolation fails closed. Effect observations and result aggregation are performed by coordinator software; Candidate tests and stdout cannot assert a verdict.

Every subprocess has recorded PID, birth, executable, group/session and Run binding. Cleanup uses exact recorded identities; ambiguity prevents PASS. Restart never resumes a verifier. A launch without a recoverable process identity remains uncertain and blocks new execution. No PID-only or unrelated process killing is allowed.

The evaluator fingerprint covers the actual host oracle, sandbox policy, materializer, aggregation, recipe, environment and cleanup code as well as the child driver. Source and compiled runtime representations have different identities; switching requires a fresh Run. Environment drift also makes prior results historical.

Each Run retains exact Candidate/tree/diff/BASE, accepted Evaluation and recipe hashes, protected bundle hash, environment/tool versions, step durations and evidence digests. Final acceptance is atomic and requires all claims PASS, complete evidence, current identities and certified cleanup. File tampering is detected by hashing evidence again. Finalized records reject update, delete, replacement and upsert. Explicit rerun creates new history.

Browser/performance adapters, generic shell recipes, debug/correction loops, reviewers and receipts are not implemented. Command Center browser checks are development verification only. Proof remains unavailable.
