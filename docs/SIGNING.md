# Sealed verdicts

Use `./cc verify <ticket>` or `./cc verify --all`. These commands open SQLite read-only, verify the ordered ticket-event chain, authenticate each post-SIGN-1 check against the trusted public key, hash the stored facts/diff, and replay the exact stored facts through the unchanged core. They never build, refresh a check, or accept a change.

Exit codes: 0 = all requested checks sealed and replaying; 1 = detected break; 2 = older/unsealed or no checks. Older events say “Not sealed (older than SIGN-1)”; no signatures are backfilled. A seal failure is reported separately and never rewrites the verdict.

The Statement follows [in-toto v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md). The payload type is application/vnd.in-toto+json and signatures cover byte-counted [DSSE PAE](https://github.com/secure-systems-lab/dsse/blob/master/protocol.md). ECDSA P-256 / SHA-256 signatures use DER encoding. The subject is the frozen diff, named by its Candidate commit; its SHA-256 is not a Git object hash.

Production verification trusts `docs/VERIFY_KEYS.json`: public keys, SHA-256 SPKI key IDs, activation/retirement times and the current key. `docs/VERIFY_KEY.pem` retains the original software PUBLIC key for compatibility; it is no longer the current signer. DSSE already binds each signature's `keyid`. Verification authenticates the signature before checking its signed timestamp against the key's interval (valid-from inclusive, valid-until exclusive). Retired signatures dated at/after retirement are rejected; earlier seals still verify. Published history must be preserved and reviewed like trusted source code.

SIGN-1b activated migration 21 on the real database after a fresh Litestream/file checkpoint and a full restore proof: 178,472 files, 51 tables, one passkey, 1,061 events, matching file/table digests and clean SQLite checks. At activation there were zero sealed check events, 19 older check events and zero broken seals. Older events remain unsealed; no history is rewritten or backfilled.

The active signer is `SECURE_ENCLAVE_P256`. An unsigned Swift/CryptoKit helper works without special entitlements on this Mac. It uses `AfterFirstUnlockThisDeviceOnly` plus `privateKeyUsage`, without `userPresence` or biometric flags: signing requires no finger and can continue after the first unlock. Before first unlock or if hardware access fails, sealing fails visibly; no software key is silently substituted. The protected signing directory holds only a device-bound blob (`device-key.blob`, 0600), public identity/mode metadata, and the host-only helper. The Secure Enclave private key is never exported. The Builder is denied reading the blob and executing the helper; the real probe verifies both. There is no signing HTTP or agent endpoint.

Rotation is explicit. Stop the recorded coordinator using its ownership controls, compile `scripts/enclave-seal.swift` with `/usr/bin/swiftc` into ignored tools, then run `node scripts/rotate-verdict-key.ts <data-dir> <compiled-helper>`. This tool requires the exclusive coordinator lock, refuses an existing blob, checks the previous published identity, proves a new signature independently, retires the previous public key and publishes the new one. Restart normally and run `./cc verify --all` before removing the exact retired private file. The SIGN-1b run overwrote/fsynced/unlinked the local software key; physical erasure from APFS/SSD snapshots is not guaranteed. Old backups retain copies; see BACKUPS.md.

A lost/replaced Mac does not need the old private key to verify history. Restore the database/evidence and obtain the reviewed published `VERIFY_KEYS.json` from source; do not restore private.pem or reuse a blob from the old Mac. On the replacement Mac, with the coordinator stopped and signing directory absent, compile the same helper and run the explicit rotation tool above. It creates a new hardware key and appends its public identity; keep every previous public entry. Publish/review that changed public history separately. New sealing waits for successful provisioning; old signatures continue verifying by their original key IDs. Private passkeys may require separate re-registration on a replacement device.

Backups retain signing public metadata, facts, sealed diffs, attestation tables and the latest chain head, but exclude exact private.pem/device-key.blob paths. Public-key history is in the source checkout. Signatures authenticate recorded checks; they do not prove test coverage. An owner/root attacker replacing trusted code/history or rolling back the database and every retained anchor remains outside this local scheme. A signed timestamp is authenticated signer data, not an independent trusted timestamp.

Examples in artifacts/sign1 use an isolated NOT CHECKED fixture and example-public.pem, not the production key. They demonstrate authentication without claiming that a real task was checked or approved. No AI study ran for the reviewer overlap; no review role qualified.
